HTML output

The HTML engine writes its output into the directory given by the dir deck attribute ("html_out" by default), which is created if needed. The directory contains:

– one HTML file for each card, named after the card's identifier, unless the card's html.file attribute specifies another name. If two cards have the same file name, the later one overwrites the earlier one, so keep the file names unique;

– style.css (or the file given by html.style.file), the style sheet shared by all files;

– a set of index files for each series: series_NAME.html, series_NAME_compact.html, series_NAME_reverse.html, series_NAME_flat.html and their combinations;

– an index file tags_TAG.html for each tag;

– feed.xml, the RSS feed, if deck.url is set (see Series and tags).

Each card is rendered as a column with a header (containing the card's title) and a footer (containing the series navigation). Each fragment and each note is preceded by an HTML anchor, named after its identifier, so any fragment or note can be linked to from outside as FILE.html#IDENTIFIER. If deck.url is set, each page also refers to the RSS feed at deck.url/feed.xml. Cards with mathematics load MathJax 3 (with the amscd package) from the jsDelivr CDN.

The output is customised with the following attributes. Remember that html.style, html.head and html.title are lists: always set them with the plus sign.

html.style on the deck: CSS appended to style.css. This is the main means of changing the look of the output. The style sheet of this manual (fonts, colours, layout of the header and footer) is defined this way in self.conf:

/// +html.style p { text-align: justify; }
/// +html.style a { color: #2288bb; text-decoration:underline; }

html.style on a card: CSS placed in a style element in the card's file.

html.style on a fragment: inline CSS for the fragment's element:

This paragraph is red.
/ +html.style color: red;

html.head: lines added to the head element of the card's file, for example, to include a script. Inherited.

html.title: a prefix for the title of each HTML file. Inherited.

html.file and html.anchor on a card, html.anchor on a fragment: override the file name and the anchor names.

The style sheet starts with built-in rules, which html.style can override. The following elements and classes are used by the generated HTML:

– .column: the column containing a card; header and footer: its header and footer;

– code.inline: inline code produced by the cd style;

– .image: the block containing an image and its caption;

– span.annotation: text with a note attached, and the notes themselves;

– span.linktarget: the target span of a link;

– .margin-left and .margin-right: the left and right margins, holding link marks, fragment identifiers and notes; span.frag-id: a fragment identifier;

– .align-left, .align-right and .align-centre: the alignment styles;

– table.no-borders: the tables of the series and tag indices.

Series and tags

Cards are organised in two ways: by series and by tags.

A series is an ordered sequence of cards. A card is placed in a series by the # attribute, whose value is the name of the series and the position of the card in it:

// +# trunk 07
// +# chrono 2025/04/01

A card can be in any number of series, but only once in each. Positions within a series must be unique and are compared as strings, so use zero-padded numbers ("07", not "7") or ISO dates. If the position is omitted, the identifier of the card is used.

The footer of each card links it to the previous and the following cards in each series the card belongs to, and to the index of the series. For each series, the HTML engine generates an index file, listing all the cards in the series with their titles, briefs and tags. The brief is cut to its first 80 characters, so keep brief attributes short. The index comes in several variants (compact or full, in direct or reverse order, as a table or "flat", that is, with the full text of all cards), and each variant links to the others.

Tags are keywords. A card is tagged with the tags attribute:

// +tags concepts
// +tags syntax

For each tag, the HTML engine generates an index file listing the tagged cards.

The series named "timeline" is special: it is used to produce the RSS feed. Each card in this series becomes an item in feed.xml, and the first ten characters of the position are used as the publication date. Use positions like "2025-04-01" or "2025-04-01 12:30" for timeline cards and set the deck.url deck attribute. Note that the date is written to the feed as is, not in the RFC 822 format required by RSS, so some feed readers may reject the feed.

Styles

card has no built-in inline markup. Instead, styles are defined by attributes, whose values are regular expressions. The following styles are available:

em: emphasis. it: italics. bd: bold. un: underline. cd: inline code. ma: inline mathematics (see Mathematics). al, ar, ac: align the text to the left, right or centre.

The regular expression must contain two named groups: open and close. The text matched by these groups is removed from the output, and the text between them is rendered in the style. This manual uses (in self.conf)

/// +it (^|[ ])(?P<open>_)[^_]*(?P<close>_)
/// +em (^|[ ])(?P<open>\*)[^*]*(?P<close>\*)
/// +un (^|[ ])(?P<open>-)[^-]*(?P<close>-)
/// +cd (^|[ ])(?P<open>`)[^`]*(?P<close>`)

so that underscores make italics, asterisks make emphasis and so on. The groups can be empty, in which case nothing is removed and the matched text is simply styled. This is used to italicise Latin abbreviations and to typeset anything that looks like a function call as code:

/// +cd (^|[ ])(?P<open>)[a-zA-Z0-9_.:]+\(\)(?P<close>)(?=[- .;!?]|$)
/// +it (?P<open>)e\.g\.(?P<close>)(?=, )

Styles are inherited, so a style can be defined for the whole deck, for a card or for a single fragment. Styles are applied to paragraphs and notes only, not to code, math or headings.

Styles are applied in a fixed order: em, it, bd, un, cd, ma, then the alignments; within one style, the expressions are tried in the order of their definition, the most specific node first. Once a style removes its markers, the later styles no longer see them, so if two styles use the same characters, only the first one has any effect.

Be careful with the expressions: they are applied to the whole paragraph text. With the definitions above, a dash at the beginning of a word starts an underlined span that ends at the next dash in the paragraph. This is why this manual uses en dashes (–) for its lists.

Notes

A note is a short text attached to a part of a fragment. The HTML engine renders notes on the right margin and underlines the part of the text they are attached to. Each note gets a colour from a cycle of six, so neighbouring notes are usually distinguishable. A note is created with

/ +* "REGEX" TEXT

where REGEX selects the part of the fragment to which the note is attached (the same rules as for the spans in links apply, see Links) and TEXT is the text of the note, extending to the end of the line. Note text is subject to styles. Lines starting with : that immediately follow set attributes of the note, for example its identifier. Example:

This paragraph talks about one thing and then another thing. A lot of
marginalia are inserted here for demonstration purposes.
/ +* "one thing" Also described in the next paragraph
: id one
/ +* "another thing" Which is actually a _generalisation_ of the one thing.
/ += !phases-syntax "sentences" -> . "marginalia"
/ += https://www.example.com -> . "inserted"
/ +* "then" Add more colours.
/ +* "demonstration" Add even more colours.
/ +* "purposes" And more

The note's regular expression cannot contain a double quote.

Notes can contain hyperlinks. A link is added to a note by a : line, in the same way as a link is added to a fragment by a / line. In a note's link attribute, . refers to the note itself:

/ +* "REGEX" TEXT
: += . "REGEX" -> TARGET

The : lines must immediately follow the note's / +* line (or each other). A link attribute can also be attached to any other fragment and refer to the note by its identifier, which is how links into notes of other cards are made:

/ += !notes-linkdemo-see "Links" -> !links-top

Links defined on the card or on the deck, including automatic links, apply to notes as well. Link attributes of the note's fragment do not: they apply to the fragment only.

A span in a note can be either end of a link. When it is the target, the matched text is underlined and the numbered mark linking back to the source is placed in the left margin of the note's fragment. Hyperlinks leading to a note, or to a span in a note, lead to the note in the right margin.

Links

A link connects two places: the source and the target. Links are added by += attributes. A link attribute value has the following grammar:

LINK           ::= SOURCE '->' TARGET
SOURCE, TARGET ::= URL | DECK_LOCATION
DECK_LOCATION  ::= NODE [SPAN]
NODE           ::= '.' | '!' IDENTIFIER
SPAN           ::= '"' REGEX '"'

. refers to the current node: the fragment to which the attribute is attached. ! IDENTIFIER refers to the node with the given identifier (see Identifiers). A span is a regular expression (in Python syntax) that selects a part of the text of the node. Anything that does not start with . or ! is a URL. Examples:

\
// id CARD0

Add a link to a web-page here ...
/ id PARA0
/ += . "here" -> https://www.example.com

Another paragraph. Link _to_ it from a particular text in the previous paragraph.
/ += !CARD0-PARA0 "a link" -> . "Link"

[0] 

When a span is the source of a link (i.e., when it is on the left-hand side of ->), the HTML engine turns the matched text into a hyperlink, like here. When a span is the target of a link, the matched text is underlined and a numbered marginal mark linking back to the source is inserted on the left. If the target is a node without a span, the hyperlink leads to the node's anchor.

The regular expression is matched against the text of the fragment as it is written in the cardfile, before styles are applied, so the source markup characters (like underscores and asterisks) are visible to it. Every match of the expression gets the link, so make the expression specific enough. Use lookaheads and lookbehinds to select a word in a particular context, as in the "EVCOMB(?=:)" example on the Syntax card. Remember that the lines of a paragraph are joined with a space, but leading blanks are preserved: use \s+ rather than a single space to match words that can be split across lines.

The URL can refer to the named groups of the expression at the other end with Python format syntax. Together with the inheritance of links, this gives automatic links. A link attribute set on a card applies to every fragment of the card, and one set on the deck applies to every fragment of the deck. This manual's self.conf contains:

/// += . "(?P<type>str|dict|set|list)\.(?P<func>[a-z.A-Z_0-9]+)\(\)" -> https://docs.python.org/3/library/stdtypes.html#{type}.{func}
/// += . "\bcard\.(?P<code>[a-z.A-Z_0-9]+)\(\)" -> https://raw.githubusercontent.com/nikitadanilov/card/refs/heads/master/card#:~:text={code}

which is how the mentions of str.split() and card.compile_deck() get their hyperlinks. Because the URL of a link with a span at the other end always goes through Python formatting, literal braces in such a URL must be doubled: write "{{" and "}}" for "{" and "}". Otherwise card reports an error.

The link attribute does not have to be attached to either end of the link. For example, the following attribute, attached to some fragment, links a word in the fragment with identifier "phases-syntax" to a word in the attached fragment:

/ += !phases-syntax "sentences" -> . "marginalia"

This works on a fragment, but not on a card or the deck. A link set on a card or the deck is created anew for every fragment and note below it. That is what makes automatic links with . work, but a link with an explicit "!" end set on a card produces as many copies of the same link as the card has fragments and notes. Put such links on a fragment.

Note that the source end of a link (the regular expression or the URL) cannot contain "->", and identifiers cannot contain spaces.

Attributes

Attributes are key-value pairs attached to nodes. card uses some of the attributes to drive the layout and its rendering by the engine. Other attributes can be used by the user for any purpose:

/ C Attribute "C" is not used by card. So it can be used to add comments
/ C to the cardfile. All hail FORTRAN!

An attribute is either a single value (set with key value) or a list of values (extended with +key value). Setting a single-valued attribute again replaces the old value.

List attributes must always be set with the plus sign, even when there is only one value. card does not complain otherwise (only --check warns), but it treats the string as a list of characters: // tags foo tags the card with "f" and "o" (twice). Conversely, +key after a plain key is an error. In the reference below, list attributes are marked [list].

Many list attributes are also inherited: when card looks up such an attribute for a fragment, it combines the values set on the fragment itself, on its card and on the deck. This is how styles and automatic links defined once in a configuration file apply to every fragment of the deck. Inherited attributes are marked [inherited] below. They can be set on the deck, on a card or on a fragment.

Deck attributes:

dir: the output directory, relative to the current directory. "html_out" by default. Use "." to write into the current directory.

engine: the output engine. Only "html" (the default) is available.

deck.title: the title of the deck, used in the RSS feed and in the reference to the feed from every page.

deck.description: the description of the deck, used in the RSS feed.

deck.url: the public URL of the output directory. If it is set, the RSS feed is generated, and every page refers to it. Required if any card is in the "timeline" series (see Series and tags).

html.style [list]: CSS appended to the generated style sheet. See HTML output.

html.style.file: the name of the generated style sheet, "style.css" by default.

html.series_compact, html.series_reverse, html.series_flat: when set to a non-empty value, the series links in card footers point to the compact, reversed or flat variant of the series index.

Inherited attributes, usually set on the deck:

em, it, bd, un, cd, ma, al, ar, ac [list, inherited]: style definitions, see Styles.

= [list, inherited]: a link, see Links. Always written as +=.

TeX [list, inherited]: TeX definitions emitted at the top of a card if it contains mathematics, see Mathematics.

html.head [list, inherited]: lines added to the head element of each HTML file.

html.title [list, inherited]: a prefix for the title of each HTML file.

frag.id.show [list, inherited]: if the first value found is "+", the identifier of each fragment is shown in the left margin. Handy when writing links.

Card attributes:

name: the title of the card, shown in its header, in the HTML title and in the indices.

label: the title of the card if name is not set. If neither is set, the title is "Card" followed by the identifier.

id: the identifier of the card (see Identifiers).

brief: a short description of the card, shown in the indices. If not set, the beginning of the card's text is used.

tags [list]: keywords under which the card is indexed:

"The only way to make a man trustworthy is to trust him."
// +tags Stimson
// +tags platitudes

# [list]: the position of the card in a series:

\
// name Card Number Three
// +# trunk 03
// +# chrono 2025/04/01

Attributes above place "Card Number Three" at position "03" in the "trunk" series and at position "2025/04/01" in the "chrono" series. See Series and tags.

html.style [list]: CSS placed in a style element in the card's file.

html.file: the name of the output file of the card. Derived from the identifier by default.

html.anchor: the HTML anchor of the card. The identifier by default.

Fragment attributes:

id: the identifier of the fragment (see Identifiers).

level: the heading level of a head fragment.

url: the source of the image of an img fragment.

width: the width of the image of an img fragment.

html.style [list]: inline CSS style of the fragment. Ignored for headings and display formulae.

html.anchor: the HTML anchor of the fragment. The identifier by default.

>: the indentation level, set by the parser from the leading >-s.

+* is not an attribute, despite the similar syntax: it creates a note, see Notes.

Any node:

DEBUG: the debugging level of the node, see Debugging and caveats. Not inherited.

Finally, card sets a few attributes itself: file, seq, mtime and ctime of a card are the name of the cardfile it came from, its sequential number in that file and the modification and change times of the file. seq of a fragment is its position in the card, and seq of a note is its position in the fragment. The HTML engine also sets card-title on cards and html.file and html.anchor on every card, fragment and note. Treat all these names as reserved.

Fragments

A fragment is the unit of content within a card. The type of a fragment is given by the ; line preceding it. The following types are supported.

para: a text paragraph. This is the default type. The lines of a paragraph are joined into one line and the result is subject to styles, links and notes.

code: a display of preformatted text. Lines are kept exactly as written (modulo the leading | and >-s). Links and notes are applied to code displays, but styles are not.

math: a display formula in TeX notation. See Mathematics.

head: a heading. The level attribute sets the heading level (1 by default):

; head
/ level 2
Inner workings

img: an image. The image is given by the url attribute (required), and its width by the width attribute ("50%" by default). The width is written into the width attribute of the HTML img element, so use a number of pixels or a percentage, not an arbitrary CSS length. The image is centred. The text of the fragment, if any, is rendered below the image, so it can be used as a caption:

; img
/ url https://upload.wikimedia.org/wikipedia/commons/4/47/PNG_transparency_demonstration_1.png
/ width 30%
Two dice.

Paragraphs, code displays and images can be indented. The number of > characters at the beginning of a line of text sets the indentation level of the whole fragment. Each level is 3em in the HTML output. The indentation of headings and display formulae is silently ignored. Indentation is used in this manual for lists: card has no special list syntax; a list is just a sequence of indented paragraphs that start with a dash. If several lines of a fragment start with >, the last one wins. Code displays can be indented in the same way: put the >-s on the first line of the code, as in the examples above.

Syntax

The cardfile syntax is extremely simple and line-oriented. The first word of a line (that is, its first sequence of non-blank characters) determines what the line means.

– An empty line marks the end of the previous fragment (if any). Multiple empty lines count as one.

– A line starting with a ; specifies the type of the immediately following fragment (one of para, code, math, head or img, see Fragments):

; code
EVCOMB: ARGS := '()
EVCOM1: TYPE-DISPATCH ON EXP INTO
                "COMBINATION": GOTO EVCOM2
                "FUNCALL": GOTO CALL
                "CONS": GOTO CONS
                "CAR": GOTO CAR
                "CDR": GOTO CDR
        HCTAPSID-EPYT
/ += . "EVCOMB(?=:)" -> https://dl.acm.org/doi/pdf/10.1145/359024.359031

; para
The previous fragment was a block display of code with an embedded link. This
fragment is a text paragraph.

If the fragment type is not specified, the next fragment will be a paragraph.

; para
This fragment is a text paragraph.

This fragment is a text paragraph too.

– A line starting with a \ indicates the beginning of a new card. This makes it possible to have multiple cards in one file. Each cardfile starts a new card implicitly.

– A line starting with /// is a deck attribute. A line starting with a // is a card attribute and a line starting with / is a fragment attribute. All attributes have the same syntax: the key and the value separated by spaces. If the key starts with +, the value is added to the list of values for the key (with + stripped). See Attributes.

– A line starting with / +* creates a note attached to the current fragment and a line starting with : is an attribute of the most recently created note. See Notes.

– All other lines are fragment text. If a line of fragment text starts with >-s, they are stripped and used to set the fragment's indentation level. If a line of fragment text starts with |, that character is stripped. | is a continuation marker used to continue the fragment when it would be otherwise terminated (e.g., over blank lines). Unlike the other markers, > and | are recognised only in the very first column of the line.

This is an example of cardfile syntax.
The next line sets attribute KEY to the value V0
/ KEY V0
Setting an attribute does not break the fragment; our paragraph continues.
Next, make a card attribute LIST with a list of values:
// +LIST element0
// +LIST element1

> This paragraph is indented.
|
The indented paragraph continues.

A few consequences of these rules are worth spelling out.

– Attribute lines can appear anywhere: a card attribute can be set in the middle of a fragment and a deck attribute can be set in any card of any cardfile. A fragment attribute, however, can only be set while a fragment is open: after its first line of text or its ; line, and before the empty line that ends it.

– Every attribute must have a value: a line consisting of just / key is an error. Values extend to the end of the line, and can contain spaces.

– Markers are recognised only as separate words. A text line starting with "/usr/bin" is a text line, because its first word is not /.

– Leading blanks do not protect a line: the line is stripped before its first word is examined. An indented C++ comment "// increment the counter" in a code display is read as a card attribute (setting "increment" to "the counter") and disappears from the output. A comment of a single word, like "// increment", has no value and makes card fail.

– To start a line of text with a word that would otherwise be interpreted as a marker, prefix the line with |. In code displays that contain lines starting with /, //, ///, ;, : or \ (after any blanks), lines starting with > or | (in the first column) and empty lines, this is required, not optional. The simplest rule is to prefix every line of a code display with |: this is how the examples in this manual are written. A literal | at the beginning of a line is written as ||.

– Leading blanks are preserved in code and math fragments. In paragraphs, lines are joined with a space, but their leading blanks are kept, which matters when writing regular expressions for links and notes (see Links).

– There are no comments as such, but attributes not used by card can serve as comments (see Attributes).
