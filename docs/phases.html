Processing phases

This card describes how card works inside. You do not need it to write decks, but it helps to understand the error messages and the caveats on the next card.

Deck processing happens in the following phases:

1. Syntax. The deck consists of one or more cardfiles. Cardfiles are read sequentially and parsed. The word "parsed" should not be taken too seriously. There is no formal grammar and the "parser" is just a bunch of str.split() and str.strip() calls. The main parser's logic is in the card.read_card_file() function. (Fun fact: the hyperlinks to the functions in the preceding sentences are generated automatically.) A cardfile consists of:

– the formatting instructions indicating the boundaries between fragments and cards,

– the text of the fragments and

– the attributes associated with a fragment or a card or a deck. An attribute is a key-value pair, where the key is a string and the value is either a string or a list of strings.

The deck, cards, fragments and notes are nodes. The parser builds a tree of nodes with the deck as the root, cards as its children, fragments as its grandchildren and notes attached to fragments at the bottom.

2. Compilation. The next phase, implemented in the card.compile_deck() function, interprets attributes to create layout instructions for the text. This happens in multiple passes:

– First, each node in the tree is assigned a unique identifier that is used to refer to it in the future. The user can specify the identifier by setting the id attribute. At the same time cards are collected according to their tags and series.

– Then, links are instantiated from the link attributes. card supports a general link mechanism: both ends of a link can be specified by a URL, an identifier of a node in the deck, or an identifier together with a regular expression.

– At the next step, styles are attached to the nodes. Styles and links are specified by regular expressions.

– Next, each fragment is lowered: the regular expressions of its links, notes and styles are matched against the text, appropriate layout commands are inserted and the text is split into pieces.

– Finally, cards and the deck are wrapped in begin and end commands and the commands of all nodes are assembled into a program for an abstract layout engine.

3. Rendering. In the final step, implemented in card.render_deck(), the abstract program is executed by an engine (only the HTML engine exists at the moment), which produces the output.
